Culprit объединяет статистику запросов, планы выполнения, ожидания и контекст схемы в единый рабочий процесс. Инструмент ранжирует выявленные проблемы по степени влияния и связывает каждую из них с доказательствами, рекомендуемым исправлением и шагами проверки. Работайте с ним в настольном приложении, терминале или через ИИ-агента для разработки.

<a id="get-started"></a>
## Быстрый старт

[Скачайте настольное приложение или автономный CLI](https://github.com/culpritsql/culprit-sql-studio/releases/latest). В приложении добавьте подключение или откройте файл SQLite, чтобы увидеть панель диагностики.

Из терминала:

```sh
culprit conn add shop --env staging --url 'postgres://app@db.example.com:5432/shop'
culprit scan shop
culprit dashboard shop
```

При повторном открытии подключения сразу отображается сохранённый отчёт, пока в фоновом режиме выполняется новое сканирование. Настольное приложение поддерживает подписанные автообновления; автономный CLI обновляется командой `culprit update`.

<details>
<summary>Попробовать интерфейс на демо-данных</summary>

Если установлен [Bun](https://bun.sh):

```sh
git clone https://github.com/culpritsql/culprit-sql-studio.git
cd culprit-sql-studio/app
bun install --frozen-lockfile
bun run dev
```

Демо-версия в браузере использует встроенные снимки состояния и не требует подключения к базе данных.

</details>

<a id="supported-databases"></a>
## Поддерживаемые базы данных

| Провайдер | Источники и возможности |
|---|---|
| [**SQL Server / Azure SQL**](../providers/mssql.md) | Query Store, кэш планов, динамические административные представления (DMV) и сохранённые события взаимоблокировок |
| [**PostgreSQL / Amazon RDS**](../providers/postgres.md) | `pg_stat_statements`, представления системного каталога и статистики, EXPLAIN и гипотетические индексы через HypoPG |
| [**TimescaleDB**](../providers/timescale.md) | Источники PostgreSQL, а также размеры гипертаблиц и управляемые/сжатые чанки |
| [**YugabyteDB**](../providers/yugabyte.md) | Нативные счётчики YSQL/DocDB, планы DIST, шардирование и изолированные источники активности |
| [**MySQL**](../providers/mysql.md) | `performance_schema`, `sys`, EXPLAIN и журнал медленных запросов (slow query log) |
| [**MariaDB**](../providers/mariadb.md) | Performance schema, журнал медленных запросов, пользовательская статистика, планы MariaDB и представления блокировок |
| [**ClickHouse**](../providers/clickhouse.md) | Журналируемые исходные запросы (`system.query_log`), куски и слияния MergeTree, мутации, репликация и `EXPLAIN PLAN` |
| [**SQLite**](../providers/sqlite.md) | Инспекция файла в режиме «только чтение», `EXPLAIN QUERY PLAN` и журналы запросов фреймворков |

Доступные функции зависят от СУБД, включённых источников и прав вашей учётной записи. Недоступные источники отображаются с указанием причины и инструкциями по настройке. Сравнение возможностей и список проверенных версий приведены в разделе [Сравнение возможностей СУБД](../parity.md).

<a id="what-you-get"></a>
## Возможности

### Выявленные проблемы: доказательства, исправления и проверка

Каждая выявленная проблема содержит затронутые запросы, временное окно измерений и фактические данные, обосновывающие её критичность. Откройте карточку проблемы, чтобы увидеть предлагаемое изменение, готовый для копирования SQL-код (когда он применим), шаги проверки и краткую сводку для коллеги или ИИ-агента.

| Область | Примеры проверок Culprit |
|---|---|
| Производительность запросов | Тяжёлые соединения (JOIN), регрессии планов выполнения, чувствительные к параметрам планы, блокирующие использование индексов преобразования типов, паттерны N+1, ошибки выполнения, таймауты и сбросы данных на диск (spills) |
| Индексы и схема | Недостающие, неиспользуемые, дублирующиеся и перекрывающиеся индексы; неиндексированные внешние ключи; риски секционирования |
| Обслуживание и ёмкость | Устаревшая статистика, мёртвые кортежи, раздувание таблиц (bloat), крупные строки, исчерпание последовательностей и риск переполнения счётчика транзакций (wraparound XID) |
| Состояние базы данных | «Горячие» строки, эскалация блокировок до уровня таблицы, задержка хранилища, повреждение контрольных сумм страниц, частое переоткрытие соединений, отставание репликации и параметры конфигурации |

Например, демо-стенд SQL Server включает план выполнения, совершающий **1,5 млрд сравнений строк**. На затронутый запрос приходится **27% времени базы данных** за пять часов. Culprit обнаруживает принудительный хинт соединения вложенными циклами (loop join), предлагает убрать его и даёт пошаговую инструкцию для сравнения нового плана выполнения и проверки результата.

Выполните `culprit checks`, чтобы просмотреть полный список проверок и необходимых для них возможностей источников.

### Планы выполнения и данные времени выполнения

Исследуйте планы выполнения в виде диаграммы, дерева с отступами или таблицы операторов. Аналитические подсказки объясняют дорогостоящие операции поиска (lookup), ошибки оценки числа строк, неэффективные соединения, сбросы на диск, преобразования типов, выделение памяти и параллелизм со ссылками на соответствующие узлы плана.

Просматривайте ожидаемое и фактическое число строк, свойства операторов и исходный XML или JSON. При необходимости запускайте точный замер поддерживаемых запросов на чтение. В SQL Server можно изучить сохранённый последний фактический план без повторного запуска запроса или в реальном времени наблюдать за прогрессом операторов выполняющегося запроса, если эти данные доступны.

### Сравнение планов и обмен ими

Вставьте, перетащите или откройте файл плана выполнения либо трассировку событий из другого инструмента — или изучите его прямо в браузере на [explain.culpritsql.com](https://explain.culpritsql.com): файлы SQL Server `.sqlplan` и `.xel`, текстовый или JSON-вывод EXPLAIN в PostgreSQL, вывод DIST в YugabyteDB, планы MySQL/MariaDB или `EXPLAIN PLAN json=1` в ClickHouse. Сравнивайте две версии плана на синхронизированных диаграммах с подсветкой изменений в операторах, методах доступа, оценках числа строк и стоимости.

Сравнение также объясняет различия в перехваченных параметрах, статистике, параллелизме и использовании памяти, если планы содержат эти сведения. Делитесь выявленными проблемами и планами в формате Markdown, в виде автономной HTML-страницы или нативного файла плана — маскирование литеральных значений включено по умолчанию.

### Активные сессии, блокировки и взаимоблокировки

Отслеживайте цепочки блокировок вплоть до удерживающей их сессии. Анализируйте ожидания, долгие запросы и транзакции, оставленные приложением открытыми. Записанные взаимоблокировки содержат тексты участвовавших запросов, схему конфликта и рекомендуемые дальнейшие действия.

Данные о текущей активности обновляются автоматически и при необходимости ставятся на паузу. На непродакшен-подключениях отменить запрос или завершить сессию можно прямо из приложения или CLI.

<a id="collector-and-culprit-fleet"></a>
## Коллектор и Culprit Fleet

Запустите `culprit collect` как ограниченный по ресурсам фоновый коллектор в режиме «только чтение», чтобы непрерывно мониторить базы данных без прямого подключения интерактивных пользователей или агентов к продакшену. Коллектор сохраняет запечатанные снимки в надёжную локальную очередь (outbox), резервирует первичные доказательства в приватных хранилищах **Azure Blob Storage** или **Amazon S3**, локально запускает детерминированный диагностический движок Culprit и публикует инциденты (`CulpritIncidentsV1`), выявленные проблемы (`CulpritFindingsV1`), изменения схемы и настроек (`CulpritChangesV1`), а также 13 таблиц первичных доказательств в **Azure Data Explorer (ADX)** или **ClickHouse**.

### 1. Локальный сбор данных или генерация DDL для хранилища

```sh
# Собрать ограниченный снимок состояния в локальную очередь outbox (хранилище не требуется)
culprit collect outbox init ./outbox
culprit collect once shop --collection activity --outbox ./outbox

# Или сгенерировать DDL таблиц и вспомогательных представлений хранилища напрямую из контейнерного образа
docker run --rm ghcr.io/culpritsql/culprit-collector:v0.6.4 \
  collect schema --store clickhouse --format sql > clickhouse-schema.sql
```

### 2. Развёртывание защищённого шарда коллектора в Kubernetes

Мультиархитектурные образы (`linux/amd64` и `linux/arm64`) публикуются в `ghcr.io/culpritsql/culprit-collector` в паре с OCI Helm-чартом, который по умолчанию создаёт ноль реплик, гарантирует монопольную запись через `StatefulSet` (`65532:65532`, корневая файловая система только для чтения) и изолирует учётные данные источников, хранилища резервных копий и аналитического хранилища:

```sh
helm upgrade --install culprit-collector \
  oci://ghcr.io/culpritsql/charts/culprit-collector \
  --version 0.6.4 \
  --namespace db-monitoring \
  --create-namespace \
  -f values.yaml
```

### 3. Расследование в Culprit Fleet, SQL Studio или CLI

Исследуйте инциденты по всему парку БД, временные окна, хронологию запросов, планы выполнения и дрейф конфигурации напрямую из ADX или ClickHouse — без единого прямого подключения к продакшен-базам:

- **Веб-консоль:** **[fleet.culpritsql.com](https://fleet.culpritsql.com)** (или собственная инсталляция `culprit-archive-web`)
- **Настольное приложение:** откройте раздел **Архивы** в боковой панели Culprit SQL Studio
- **CLI и MCP:** `culprit resources`, `culprit window`, `culprit incident`, `culprit collect queries` (дашборды и правила алертинга Grafana) и `culprit mcp --warehouse-evidence`

[Архитектура коллектора и хранилища →](../collector.md) · [Helm-чарт для Kubernetes →](../../deploy/helm/culprit-collector/README.md)

<a id="coding-agents-and-ci"></a>
## ИИ-агенты для разработки и CI

### MCP и настройка репозитория

Встроенный MCP-сервер открывает Claude Code, Cursor, Codex и другим MCP-клиентам доступ к выявленным проблемам, планам выполнения запросов, схеме, проверке миграций, блокировкам, ожиданиям, рекомендациям по индексам и шагам верификации. Агенты обращаются к базам по именам сохранённых подключений, а учётные данные не покидают Culprit.

```sh
claude mcp add culprit -- culprit mcp
culprit agent init --connection shop
```

Вторая команда добавляет инструкции в репозиторий и конфигурацию MCP. В других клиентах достаточно зарегистрировать команду `culprit` с аргументом `mcp`. Если комментарии в SQL-запросах содержат ссылки вида `file:line` (включая аннотации Marginalia и SqlCommenter), сводки по проблемам указывают прямо на соответствующие строки кода приложения.

Выведите сводку по конкретной проблеме или проверьте предлагаемый индекс PostgreSQL через HypoPG без реального создания индекса:

```sh
culprit show shop 'filtered-scan:public.orders'
culprit explain shop --sql "SELECT * FROM orders WHERE status = 'open'" \
  --with-index "CREATE INDEX ON orders (status ASC)"
```

Уровень доступа задаётся отдельно для каждого подключения: отключён, только статистика и расчётные планы (по умолчанию) либо одобренные запросы только на чтение. При запросе подтверждения отображается точный текст SQL-выражения, а все вызовы инструментов фиксируются в локальном журнале аудита.

### Проверка миграций и процессы развёртывания

Проверяйте файлы миграций с учётом размеров таблиц, типов столбцов, индексов и записанной нагрузки из сохранённого снимка состояния. Проверки выявляют блокирующие операции `CREATE INDEX` и `ALTER TABLE`, отсутствующие или несовпадающие по типам индексы внешних ключей, а также операции `DROP` и `RENAME`, затрагивающие реальные запросы из рабочей нагрузки.

```sh
culprit lint-sql prod-snapshot.json --file migrations/ --fail-on high
culprit lint-sql prod-snapshot.json --file migrations/ --format sarif > culprit.sarif
```

Флаг `--fail-on high` завершает проверку в CI с ошибкой при обнаружении проблем высокой критичности. Флаг `--write` автоматически применяет поддерживаемые безопасные перезаписи к файлам миграций. Вывод в формате JSON удобен для скриптов, SARIF интегрируется с системами ревью кода, а стабильные идентификаторы проблем позволяют отслеживать одну и ту же проблему от сканирования к сканированию.

После развёртывания отметьте релиз на шкале времени, проверьте устранение проблемы или сформируйте обезличенную сводку:

```sh
culprit mark shop deploy v2.4.0
culprit verify shop 'filtered-scan:public.orders'
culprit digest shop > digest.json
```

## Использование в продакшене

- **Сканирование читает только статистику и представления системного каталога** с учётом специфичных для каждой СУБД таймаутов и защитных ограничений при построении планов.
- **Исправления базы данных предлагаются в виде рекомендаций**, которые вы проверяете и применяете самостоятельно.
- **Выполнение запросов на продакшене требует подтверждения** для любых выражений, которые Culprit не может однозначно классифицировать как чтение; разрушающие операции требуют дополнительного подтверждения.
- **Доступ агентов к выполнению запросов включается явно**, с индивидуальным одобрением каждого запроса на чтение и записью в локальный журнал аудита.
- **Сохранённые пароли хранятся в системной связке ключей ОС.** Для Entra ID можно использовать текущую авторизацию Azure; при экспорте для совместного доступа литеральные значения скрываются по умолчанию.

Используйте учётную запись базы данных только с теми правами, которые необходимы для вашего сценария работы. Границы сбора данных, построения планов и выполнения запросов подробно описаны в [руководстве по безопасности](../guide.md#safety) и [документации по провайдерам](../parity.md).

## Разработка

Culprit написан на Rust, Tauri и React. Настольное приложение, CLI и MCP-сервер используют единый аналитический движок. Собственные проверки и провайдеры баз данных подключаются через Rust API без необходимости форкать проект, а весь пользовательский текст загружается из [языковых каталогов](../localization.md).

<details>
<summary>Сборка из исходного кода</summary>

Установите [Rust stable](https://rustup.rs) и [Bun](https://bun.sh). В Linux также потребуются [платформенные зависимости](../guide.md#platforms).

```sh
git clone https://github.com/culpritsql/culprit-sql-studio.git
cd culprit-sql-studio

# CLI
cargo build --locked --release -p culprit-cli

# Настольное приложение
cd app
bun install --frozen-lockfile
bunx tauri build
```

</details>
